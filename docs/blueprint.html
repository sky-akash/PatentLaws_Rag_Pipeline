Patent Law Navigator Blueprint

How a question about European patent law becomes a checked, cited explanation: where the law comes from, how it is stored and searched, which models are called, and what the code verifies before anything reaches the screen.

372EPC provisions indexed 438passages 422cross-reference links 3.8 sper answer (measured) ~5.3Ktokens per answer 23offline tests

01The whole system

The app has two halves that never run at the same time. The build half runs once whenever the law is updated: it downloads the EPO pages, cuts them into passages and indexes them. The ask half runs for every question: it reads those indexes, calls the language models and checks their output. The stores in the middle are the only thing the two halves share.

Python code (deterministic) LLM call on Groq data store on disk outside the app

02Building the index

Run with python -m patentlaw.fetch epc then python -m patentlaw.index epc. Every EPO legal page carries the site's whole table of contents as a JavaScript array (var oMenu = [...]). The fetcher reads that array, so it never guesses URLs or misses a page. It keeps about 2% of each page: the metadata tags, the heading, the legal text and the footnotes.

Deleted articles (e.g. Art. 102, removed in the 2000 revision) are kept as one-line provisions, so a question about them gets "deleted" instead of silence. The EPO Guidelines (1,858 pages) use the same parser. Their pages are being downloaded and will be indexed as a second corpus.

04Life of a question

Measured on "What is the difference between Article 54(2) and Article 54(3) prior art?" with an empty cache. Time and tokens are both drawn to scale. The answer model takes most of each, which is why the reading budget is the main cost lever.

Step by step

  • API. POST /api/ask {question, use_plan}. Pydantic validates 3–4,000 characters. The cache key is sha1(answer model | use_plan | question).
  • ① Plan (gpt-oss-20b, ~550 tokens). Returns the language, whether the question is in scope, a one-line restatement, 3–5 search queries in the EPC's own vocabulary, and up to 6 provisions it suspects apply. A failed plan is not fatal: retrieval falls back to the question alone.
  • ② Retrieve (local). Turns the question, the rewrites and the guesses into ≤10 numbered sources, each tagged with why it was picked. Detailed in section 5.
  • ③ Answer (gpt-oss-120b, strict JSON schema). Reads the question plus the numbered sources and writes the fixed structure in section 6. If the big model is rate-limited for more than 30 s, the small model answers instead and the response says so.
  • ④ Verify (code). Checks every citation against the sources and the database and attaches the verbatim law. It also caps confidence when the answer begins "It depends".
  • ⑤ Judge (gpt-oss-20b). Reads each explanation next to the full provision text and rates it. Flagged items sink to the bottom with a visible note.
  • Return. The JSON goes to the browser and into the cache. app.js renders one card per field and opens any provision in a side drawer through GET /api/provision/{ref}.

05Retrieval algorithm

Retrieval decides which law the model is allowed to read, so most of the engineering sits here. Four kinds of evidence are ranked separately and then fused. The trace below is the real run for "I presented my invention at a trade fair in Munich four months ago and haven't filed yet. Can I still get a European patent?" Highlighted cells are the provision that matters, Art. 55.

The scoring rule

score(passage) = Σ over lists L containing it: wL / (60 + rankL)

Reciprocal rank fusion only uses ranks, never raw scores, so BM25 numbers (unbounded) and cosine similarities (0–1) can be combined without any calibration. A passage ranked 1st in one list earns 1/61 ≈ 0.016 at weight 1.0. The constant 60 is the standard choice from the original RRF paper; it flattens the advantage of rank 1 over rank 5.

SignalHow it ranksWeightWhat it catches
Named provisionsrefs.find_refs regexes (English and Italian, ranges like "Articles 52 to 57"), exact lookup2.0"What does Art. 123(2) mean?" always starts with Art. 123
Planner guessesthe small model's suggested provisions, kept only if they exist in the index0.4the right article when the user's words share nothing with it
BM25 keywordSQLite FTS5, porter stemming, OR of non-stop words plus an EPC thesaurus (deadline → time limit, add → amend, brevetto → patent); column weights header 4 · text 1 · keywords 0.31.0 · 0.3exact legal terms such as "divisional", "priority" or "Rule 71(3)"
Vector meaningnomic-embed-text with search_query: prefix, Chroma HNSW cosine, top 301.0 · 0.3paraphrases ("can't be described in words" → deposit of biological material)

The first weight is for the user's own question, the second for each planner rewrite. Five rewrites at 0.3 add up to 1.5, so together they help without drowning out the question. All the weights and the 0.5 cut-off were chosen by grid search on the tuning set, using cached plans so the search cost no tokens.

06The answer contract

The answer model must return JSON that matches a schema. Groq enforces this with constrained decoding (response_format: json_schema, strict: true), so every field can be checked and rendered without parsing prose. Each field maps to one card on the page.

The system prompt also sets the legal hierarchy (the Articles prevail over the Rules under Art. 164(2) EPC; the Guidelines are practice, not binding law). It forbids inventing provisions, paragraph numbers, decision numbers, deadlines or amounts. It requires the answer in the user's language, with the field names kept in English.

07Verify and judge

Two layers check every provision the answer relies on. The first is plain code and catches wrong references. The second is a model and catches wrong explanations of the right reference.

Why the judge exists: in an early run the model cited Rule 36 as "an application may be filed at any time". Rule 36 is real and was retrieved, so code checks passed, but it governs divisional applications. Only a reader who compares the explanation with the text catches that.

09Evaluation

10Limits and failure modes

What happens when something is missing

ConditionBehaviour
No GROQ_API_KEYSearch and browsing still work; /api/ask answers 503 with "paste your key into .env"; the header dot turns red
Ollama not runningVector search is skipped and retrieval continues on BM25; /api/health reports vector_search: false
Big model rate-limited > 30 sThe small model writes the answer; the response names the model used
Planner failsRetrieval uses the question alone
Judge failsThe answer is shown with judged: false and no faithfulness score
Nothing relevant foundNo model call; the page suggests naming a provision or rephrasing

Known weaknesses (observed, not hypothetical)

  • Linked concepts without links. "I missed a time limit" finds further processing (Art. 121) but not re-establishment (Art. 122). Art. 121 mentions re-establishment in words but has no hyperlink, so the graph walk can't follow it.
  • Distinctions that live in another article. For Art. 54(2) vs 54(3), the key consequence (54(3) art is ignored for inventive step) is in Art. 56, which wasn't retrieved, so the answer leaves it out.
  • The judge can be wrong. In the same run it marked Art. 54(2) "not relevant" to a question about Art. 54(2). Its flags are shown as checks to read, not as truth.
  • Weak sources still get in. Rule 132 and Art. 83 passed the cut-off for the trade-fair question. The prompt tells the model to ignore irrelevant sources, but it sometimes cites them as "related".
  • Small evaluation sets. One question moves recall by 0.02–0.06, so differences under ~0.05 are noise.
  • Coverage. EPC only so far. No Guidelines (downloading), no case law, no national law, no UPC. Answers say so in "Not covered by the sources".
